# Нефункциональные требования (NFR)

Здесь описаны требования к качеству работы системы, а не к её функциям.

## 1. Производительность (Performance)
* **NFR-01 (Скорость поиска):** Выдача списка рецептов по 2–3 ингредиентам должна занимать не более **500 мс** при 95-м перцентиле (p95).
* **NFR-02 (Расчет КБЖУ):** Расчет КБЖУ на порцию и агрегация цен из ближайших магазинов не должны задерживать ответ API более чем на **1 секунду**.

## 2. Масштабируемость (Scalability)
* **NFR-03 (База рецептов):** Система должна сохранять работоспособность при росте базы до **10 000 рецептов** и **5 000 ингредиентов**.
* **NFR-04 (Геопоиск):** Поиск магазинов поблизости (радиус 2 км) должен работать при плотности до 50 магазинов в этом радиусе.

## 3. Доступность и надежность (Availability & Reliability)
* **NFR-05 (Доступность):** Сервис должен быть доступен **99.5%** времени в месяц (допустимый простой ~3.5 часа).
* **NFR-06 (Отказоустойчивость):** Если сторонний API магазина (например, парсер цен) недоступен, система должна показывать рецепт без цен, но с плашкой «Цены временно недоступны», а не падать с ошибкой 500.

## 4. Безопасность (Security)
* **NFR-07 (Валидация данных):** Все входящие запросы (ввод ингредиентов) должны проходить валидацию на стороне сервера (защита от SQL-инъекций и XSS).
* **NFR-08 (Приватность):** Геолокация пользователя используется только для поиска магазинов и не сохраняется в базе данных без явного согласия.

## 5. Удобство использования (Usability)
* **NFR-09 (Адаптивность):** Интерфейс должен корректно отображаться на экранах смартфонов (от 375px) и десктопов (до 1920px).
* **NFR-10 (Понятность):** Время от ввода ингредиентов до отображения первых результатов не должно превышать **2 секунд** с учетом загрузки интерфейса (из постановки проблемы).
