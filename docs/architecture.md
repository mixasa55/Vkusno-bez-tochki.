# Архитектура системы и принятые решения

## 1. Стиль архитектуры: Модульный монолит
**Решение:** Используем модульный монолит (Modular Monolith).
**Обоснование:** Команда из 2 человек, учебный проект. Микросервисы потребуют сложной настройки сети, брокеров сообщений и распределенных транзакций, что замедлит разработку. Монолит позволит быстро запустить MVP, но мы разделим код на изолированные модули (пакеты), чтобы в будущем их можно было легко вынести в отдельные сервисы.

## 2. Основные модули (Bounded Contexts)
* **Recipes (Рецепты):** Управление базой рецептов и ингредиентов. Поиск по совпадению.
* **Nutrition (КБЖУ):** Расчет калорий и БЖУ на порцию, фильтрация по профилю пользователя.
* **Prices (Цены и Магазины):** Хранение геоданных магазинов, агрегация цен, расчет стоимости «докупок».
* **Recommendations (Рекомендации):** Эвристика «что еще купить» и «похожие рецепты» на основе истории.

## 3. Внешние интеграции
* **Парсер цен:** Отдельный фоновый процесс (Worker), который раз в сутки обновляет цены на продукты в магазинах. Вынесен из основного потока запросов, чтобы не тормозить поиск.
* **Геолокация:** Клиент передает координаты, бэкенд считает расстояние по формуле гаверсинусов.

## 4. Технологический стек (предварительный)
* **Backend:** Python (FastAPI) или Node.js (NestJS) — быстро разрабатывать, удобная валидация.
* **База данных:** PostgreSQL + PostGIS (для геопоиска магазинов).
* **Frontend:** React или Vue.js (SPA).
* **Инфраструктура:** Docker, docker-compose (для локального запуска БД и бэкенда).

## 5. Архитектурные решения (ADR - Architecture Decision Records)
Ниже зафиксированы ключевые решения, чтобы через полгода никто не спрашивал «почему так сделано».

* **ADR-001: Хранение цен в отдельной таблице.**
  * *Контекст:* Цены в магазинах меняются каждый день.
  * *Решение:* Не храним цену в сущности «Ингредиент». Создаем отдельную таблицу `ProductPrice` с историей.
  * *Последствия:* Усложняется запрос (нужен JOIN), но мы можем смотреть динамику цен и легко обновлять данные парсером.
* **ADR-002: Кэширование популярных рецептов.**
  * *Контекст:* Запрос «курица, рис» будет очень частым.
  * *Решение:* Использовать Redis (или кэш в памяти на первое время) для хранения топ-100 запросов на 10 минут.
