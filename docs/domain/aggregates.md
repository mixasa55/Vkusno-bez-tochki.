# Агрегаты (ЛР 2Б)

Правило для всех агрегатов: за пределы агрегата выходят только по ID. Никаких ссылок на объекты чужого агрегата.

## Рецепт (Recipe) — основной агрегат

- **Корень**: `Recipe`
- **Контекст**: Рецепты

### Состав

| Элемент | Вид | Почему так |
|---|---|---|
| `Recipe` | Сущность, корень | Имеет ID, меняется со временем: правят состав, добавляют шаги. |
| `RecipeIngredient` | Сущность внутри агрегата | Принадлежит одному рецепту, живёт и удаляется вместе с ним. |
| `CookingStep` | Сущность внутри агрегата | Порядок шагов важен и меняется только вместе с рецептом. |
| `Nutrition` | Значение | КБЖУ **на 100 г** ингредиента из справочника. Определяется числами, своего ID нет. |
| `PortionNutrition` | Значение (вычисляемое) | КБЖУ на порцию. Производное от `Nutrition` и количеств `RecipeIngredient`. В базе не хранится. |
| `Servings` | Значение | Число порций. Меняется целиком, части у него нет. |
| `Ingredient` | Сущность вне агрегата | Справочник: один ингредиент входит в сотни рецептов, живёт своей жизнью. |

### Инварианты

| № | Инвариант | Почему это инвариант агрегата |
|---|---|---|
| И-1 | `Nutrition` (белки, жиры, углеводы, ккал на 100 г) не может быть отрицательным | Проверяется по данным самого агрегата. |
| И-2 | Время приготовления > 0 | По данным агрегата. |
| И-3 | `Servings` — целое положительное число | От него делится `PortionNutrition`; при нуле расчёт неопределён. |
| И-4 | В `RecipeIngredient` количество > 0 | Состав с нулевым или отрицательным количеством бессмысленен. |
| И-5 | Порядок `CookingStep` не пропускает значений и не повторяется | Иначе инструкция рвётся при показе. |
| И-6 | Один и тот же ингредиент не встречается в составе дважды | Иначе `PortionNutrition` посчитается дважды. |

### Что инвариантом не является

| Правило | Почему не инвариант | Где проверяется |
|---|---|---|
| «Рецепт подходит пользователю» | Нужен ввод пользователя — данные другого агрегата. | Правило поиска в контексте Рецепты (`MatchScore`). |
| «Недостающих ингредиентов не больше двух» | Зависит от того, что у пользователя есть. | Слой поиска, `BR-02`. |
| «Стоимость докупки в бюджете» | Данные контекста Цены. | Контекст Цены, читает `PriceSnapshot`. |
| «КБЖУ порции ≤ 500 ккал» | Это фильтр пользователя, а не правило целостности рецепта. | `FR-04`, слой фильтрации. |

### События

| Событие | Когда | Что несет |
|---|---|---|
| `RecipeCreated` | Создали рецепт | ID, название, состав, шаги. |
| `RecipeUpdated` | Изменили состав или шаги | ID, изменившиеся поля. |
| `PortionNutritionCalculated` | Открыли карточку | ID рецепта, ккал/Б/Ж/У на порцию. |

### Границы

- Состав и шаги — внутри агрегата: меняем рецепт целиком в одной транзакции.
- `Ingredient` — снаружи, ссылка по `ingredient_id`. Меняем справочник — рецепта не касаемся.
- `PortionNutrition` не хранится: при изменении справочного `Nutrition` карточка посчитается заново сама (см. В-3 в `event-storming.md`).

## Магазин (Store) — поддерживающий агрегат

- **Корень**: `Store`
- **Контекст**: Цены и магазины

### Состав

| Элемент | Вид | Почему так |
|---|---|---|
| `Store` | Сущность, корень | Имеет ID и адрес, открывается и закрывается. |
| `StoreProduct` | Сущность внутри агрегата | Позиция товара конкретной точки; вне магазина не существует. |
| `Price` | Значение | Стоимость `StoreProduct` на момент снимка. |
| `PriceSnapshot` | Сущность, отдельный корень | Набор цен одного прогона парсера; переживает изменение магазина, поэтому не внутри `Store`. |
| `Ingredient` | Сущность чужого контекста | Ссылка по `ingredient_id`, объект справочника внутрь агрегата не берём. |

### Инварианты

| № | Инвариант | Почему это инвариант агрегата |
|---|---|---|
| И-7 | Цена не может быть отрицательной | Проверяется по данным агрегата. |
| И-8 | Широта в [-90; 90], долгота в [-180; 180] | Иначе «ближайший магазин» считается неверно. |
| И-9 | У `StoreProduct` указан `ingredient_id` | Без связи со справочником позиция не участвует в расчёте стоимости докупки. |
| И-10 | `PriceSnapshot` имеет момент сбора и TTL | Иначе непонятно, устарели ли цены (событие «Снимок цен устарел»). |

### Что инвариантом не является

| Правило | Почему не инвариант | Где проверяется |
|---|---|---|
| «Цены актуальны» | Зависит от внешнего источника и расписания парсера, а не от данных агрегата. | Фоновый парсер + TTL снимка. |
| «Магазин в радиусе 2 км от пользователя» | Нужна геолокация пользователя. | Слой выбора ближайших магазинов (`AC-03.3`). |
| «Цена ниже средней по городу» | Требует данных по всем магазинам сразу. | Аналитика, вне MVP. |

### События

| Событие | Когда | Что несет |
|---|---|---|
| `PriceSnapshotCreated` | Парсер закончил прогон | ID снимка, ID магазина, набор цен. |
| `PriceSnapshotExpired` | Истёк TTL | ID снимка, момент сбора. |
| `StoreClosed` | Магазин закрылся | ID магазина, дату закрытия. |

### Границы

- Один магазин — один агрегат: прогон парсера по одной точке не блокирует другие.
- `PriceSnapshot` — отдельный корень: его читают без открытия `Store`, и он не меняется после создания.
- В контекст Рецепты наружу отдаём только `ingredient_id` и цену, без объектов магазина.

## Почему именно так, а не иначе

- `Recipe` не включает `Store`: у них разный ритм изменения (рецепт правит человек, цены — парсер) и разный источник истины.
- `PriceSnapshot` не входит в `Recipe`: рецепт не должен переоткрываться из-за обновления цен, иначе И-6 и И-1 пришлось бы проверять под одним замком с ценами.
- `Ingredient` не входит в `Recipe`: иначе правка КБЖУ в справочнике требовала бы перезаписи всех рецептов.
