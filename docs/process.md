## Ритм команды (облегчённый процесс, не полный Scrum)

- Еженедельная синхронизация 30 мин: что сделано, что мешает, что берём на неделю
- Задачи ведём в GitHub Projects (колонки: Бэклог, В работе, На ревью, Готово)
- WIP-limit: не больше 2 задач «В работе» на человека
- Ревью: в течение суток
- Ретроспектива — раз в две недели, 20 мин

## Как принимаем решения

- Технические — тот, кто отвечает за зону, после обсуждения со вторым
- Продуктовые — консенсус; при расхождении решает ответственный за продукт
- Спорные — фиксируем в CHANGELOG с обоснованием

## Определение готовности (DoR)

Задачу можно брать в работу, если:
- [ ] Есть критерии приёмки в формате Дано – Когда – Тогда
- [ ] Указано, какой истории из карты она соответствует
- [ ] Понятно, каким изменением в интерфейсе или API она проявится
- [ ] Нет незакрытых вопросов к формулировке
- [ ] Задача помещается в одну неделю; если нет — разбита

## Определение завершённости (DoD)

Задача считается сделанной, если:
- [ ] Код влит в основную ветку через запрос на слияние
- [ ] Запрос прошёл ревью второго участника с содержательными комментариями
- [ ] Конвейер проверок зелёный
- [ ] Написаны тесты на критерии приёмки, они проходят
- [ ] Документация обновлена: README или соответствующий файл в docs/
- [ ] Добавлена запись в CHANGELOG.md
- [ ] Изменение проверено на чистом окружении

## Инструменты

| Документы | Markdown | Обязательно |

## Использование AI-инструментов

Инструменты на основе языковых моделей используются как соавтор, а не автор.

**Допустимо отдать:**
- Черновик постановки проблемы
- Генерация типовых персон по описанию домена
- Черновик карты пути и списка историй
- Типовые этапы семестрового плана

**Не доверяется:**
- Выбор домена
- Финальная формулировка постановки проблемы
- Карты и план без проверки здравым смыслом
- Спорные продуктовые решения
